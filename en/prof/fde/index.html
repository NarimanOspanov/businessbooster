The whole map as text

The same stages and topics in one list: easy to read, print or send to a friend. One end-to-end project runs through every stage, so by the end you'll have a working system for a "client" and a story to tell in interviews.

Stage 1. Understand the role

An FDE is a mix of developer, consultant, and product manager. First, figure out what you're signing up for: this is not "a programmer who sometimes calls the client."

End-to-end project, step 1
Pick an industry you know for your end-to-end project, like logistics, a clinic, or a store. Describe on one page who the client is, what hurts, and what changes once that pain is gone.

What is an FDE

Core · ≈ 1 h

An engineer sent straight to the client so the company's technology actually works for them: half programmer, half translator between AI and business.

What to learn
  • How an FDE differs from a regular product developer
  • Why AI you bought changes nothing without integration and the client's data
  • Where FDEs work: on-site, remotely, on business trips

How client work is organized

Core · ≈ 1 h

A project runs in a cycle: kickoff and scope, prototype, pilot, production, and handoff to the client's team, with feedback flowing back into the product.

What to learn
  • The cycle: kickoff → prototype → pilot → production → handoff
  • How success is measured: time, money, quality
  • How an FDE differs from a Solutions Engineer and a consultant

How much it pays

Core · ≈ 1 h

FDE is one of the best-paid engineering roles: income includes base salary, bonuses, and equity, and the level depends heavily on the country and the company.

What to learn
  • What income is made of: salary, bonus, stock
  • How to compare annual and monthly numbers
  • Why salaries differ several times over between countries

Strengths and drawbacks

Core · ≈ 1 h

The role gives fast growth and visible results, but it means travel, work without clear requirements, and constant communication. It's not for everyone.

What to learn
  • Pros: growth, impact, variety of work
  • Cons: workload, travel, uncertainty
  • Qualities that matter more than the stack: ownership, clear speaking, speed

A day in the life of an FDE

Core · ≈ 1 h

An FDE's day is questions for the client's staff, code, checking quality on real examples, and a short status update in the evening.

What to learn
  • Why you ask about yesterday's work, not about wishes
  • How to measure solution quality with numbers
  • What a typical workday at the client looks like

Your first code at a client

Core · ≈ 1 h

The first code is usually small: read the client's export, clean it, ask the model, and save the result, but do it safely and reliably.

What to learn
  • A small pipeline: read → clean → ask the model → save
  • Why you clean data before sending it to the model
  • Access keys never in the code; timeouts always

What's next: the outlook

Core · ≈ 1 h

Some of the routine will go to machines, but understanding the client, framing the problem, and owning the result will stay human work, and that's where FDE career paths come from.

What to learn
  • What in FDE work gets automated first
  • What stays with humans
  • Where to grow: architect, team lead, industry expert, your own product

Stage 2. Programming foundations

An FDE writes a lot of code, fast, inside unfamiliar systems. You need solid Python, the ability to read other people's code, and comfort in the terminal.

End-to-end project, step 2
Create a GitHub repository for the project. Write a Python script that reads a client data export (CSV) and prints the three key numbers from it.

Python

Core · ≈ 80 h

The FDE's main language: integrations, data processing, and almost everything around AI models are written in it. You need a level where the language doesn't get in the way of thinking about the problem.

What to learn
  • Types, collections, functions, classes, exceptions
  • Virtual environments, pip/uv, dependencies
  • Working with files, JSON, CSV, dates, and time zones
  • Type hints and pydantic
  • async/await for parallel API requests
Practice
Write a command-line tool that takes a path to a folder of CSV files, merges them, removes duplicates, and saves a report.
Check yourself
  • How is a list different from a generator, and when does it matter?
  • How do you isolate the dependencies of two projects on one machine?

Git and GitHub

Core · ≈ 10 h

All the code at a client lives in repositories, often the client's own, with their own rules. You need to branch confidently, resolve conflicts, and write clear pull requests.

What to learn
  • commit, branch, merge, rebase
  • Resolving conflicts
  • Pull requests and code review
  • What must never end up in a repo: keys and personal data
Practice
Create a branch in your project, make changes, and open a pull request with a description: what, why, how to test.
Check yourself
  • How do you remove an accidentally committed key from history, and what do you do with the key itself?
Resources
  • Pro Git book

Terminal and Linux

Core · ≈ 15 h

Client servers are almost always Linux, often with no graphical interface and limited access. You need to find logs, a process, and the cause of an error using only the terminal.

What to learn
  • Navigation, permissions, processes, environment variables
  • grep, find, tail -f, curl, jq
  • ssh and keys
  • Simple bash scripts
Practice
Connect to any cloud server over ssh and find the last 20 errors in the logs with a single command.
Check yourself
  • How do you find out which process is using port 8080?

HTTP, REST, and JSON

Core · ≈ 10 h

Almost every integration is HTTP requests between systems. An FDE should read a request and response as plain text and immediately see what went wrong.

What to learn
  • Methods, headers, status codes
  • REST: resources and idempotency
  • JSON and schemas
  • Postman, curl, the Network tab in the browser
Practice
Call a public API three ways: curl, Python (httpx), and Postman. Break the request and figure out the error.
Check yourself
  • How is 401 different from 403?
  • Why can retrying a POST request create a duplicate?

Reading other people's code and debugging

Core · ≈ 20 h

At a client you constantly land in someone else's systems with no documentation. The key skill is quickly understanding unfamiliar code and finding the cause of a failure.

What to learn
  • The debugger: breakpoints, stepping through code
  • Logs as the first source of truth
  • Binary search for the cause: what changed and when
  • A minimal reproduction of the bug
Practice
Take any open-source project on GitHub, find an issue describing a bug, and reproduce it locally.
Check yourself
  • Where do you start if "everything broke at the client" and nothing else is known?

Stage 3. Data

The value of AI for a client lives in their data. And that data is always messy: mixed formats, duplicates, Excel files with merged cells. An FDE spends most of their time here.

End-to-end project, step 3
Load your project data into PostgreSQL. Describe the schema and write 5 SQL queries that answer the "client's" questions.

SQL

Core · ≈ 40 h

The language all corporate data speaks. You need it to the point where you calmly write a query with several JOINs, groupings, and window functions.

What to learn
  • SELECT, WHERE, JOIN, GROUP BY
  • Subqueries and CTEs (WITH)
  • Window functions
  • Indexes and the query plan (EXPLAIN)
  • Transactions
Practice
Find the top 10 customers by revenue for each month in a single query.
Check yourself
  • Why can a LEFT JOIN unexpectedly multiply rows?

Data modeling

Core · ≈ 10 h

To build a product in, you need to understand how the client's entities are structured: order, contract, patient, shipment. A bad data model breaks everything built on top of it.

What to learn
  • Entities, relationships, keys
  • Normalization and when to break it
  • Reference tables and change history
  • How to read someone else's database schema in an hour
Practice
Draw a data schema for a fictional clinic: patients, doctors, appointments, lab tests.
Check yourself
  • How do you store a product's price if it changes over time?

Data wrangling: pandas

Core · ≈ 25 h

Fast analysis and cleanup of the exports the client sends you. It lets you answer "what's actually in this data" within an hour.

What to learn
  • DataFrame: filters, groupings, joins
  • Missing values, duplicates, types
  • Excel and CSV in different encodings
  • Simple charts for conversations with the client
Practice
Take a "messy" Excel file with merged cells and turn it into a clean table.
Check yourself
  • How do you find duplicates when names are written differently ("Alpha LLC" and "LLC Alpha")?

Pipelines and data quality

Core · ≈ 20 h

A one-off export is a prototype. In production, data has to arrive on its own every day, and the system has to notice when it breaks.

What to learn
  • ETL and ELT
  • Incremental loading
  • Quality checks: empty fields, outliers, duplicates
  • Schedulers: cron, Airflow, or similar
Practice
Write a script that pulls new rows every hour and logs a warning if no data arrived.
Check yourself
  • What happens to the report if loading fails halfway? How do you prevent that?

Documents: PDFs, scans, email

Optional · ≈ 15 h

A huge share of a client's knowledge lives not in databases but in contracts, manuals, emails, and scans. It's the main data source for AI assistants.

What to learn
  • Extracting text from PDF and Word
  • OCR for scans
  • Tables inside documents
  • Metadata: author, date, version
Practice
Extract text and tables from 20 different PDFs and count how many came out without errors.
Check yourself
  • How do you tell which of two contract versions is the one in force?

Stage 4. Backend and integrations

An FDE's solution almost never lives on its own: it pulls data from the CRM, writes to the ERP, and lets users in through corporate sign-on. Integrations are most of the code.

End-to-end project, step 4
Wrap your project logic in a FastAPI service: one endpoint takes a question, another returns a report. Add API key authentication.

Your own API service

Core · ≈ 25 h

For the client's systems to use your solution, it has to be a service with a clear API.

What to learn
  • FastAPI (or Express): routes, validation, errors
  • API documentation (OpenAPI)
  • Pagination, API versioning
  • API tests
Practice
Build a service with three endpoints and auto-generated docs, and cover them with tests.
Check yourself
  • How do you change an API without breaking the people already using it?
Resources
  • FastAPI

Authorization: OAuth, SSO, keys

Core · ≈ 15 h

In a corporation nobody creates new passwords: people sign in through corporate single sign-on (SSO), and systems use tokens. A mistake here is a security problem for the client.

What to learn
  • API keys and how to store them
  • OAuth 2.0 and OpenID Connect
  • SSO with Microsoft Entra ID, Google, Okta
  • Roles and access permissions
Practice
Add Google or Microsoft sign-in to your service.
Check yourself
  • Why shouldn't you keep a token in the code, or in localStorage unless you have to?
Resources
  • OAuth 2.0

Webhooks and queues

Core · ≈ 10 h

Client systems report events in different ways: webhooks, queues, sometimes an email. A reliable integration never loses events and never processes them twice.

What to learn
  • Webhooks and signature verification
  • Queues: RabbitMQ, SQS, Service Bus
  • Retries and idempotency
  • Polling, when there's nothing else
Practice
Receive a webhook, put the event in a queue, and process it in a separate worker.
Check yourself
  • What happens if your service was down for 10 minutes while webhooks kept coming?

Enterprise systems

Optional · ≈ 15 h

CRM, ERP, accounting systems, SharePoint: that's where the client's data lives. They often have awkward APIs, rate limits, and their own admins you can't do anything without.

What to learn
  • Typical systems: Salesforce, SAP, Microsoft Dynamics, HubSpot, SharePoint
  • Rate limits and bulk exports
  • The client's test environment and access
  • How to work things out with the client's IT department
Practice
Connect to a free developer edition of any CRM and export a month of deals.
Check yourself
  • Who at the client do you ask for system access, and what do you prepare for that conversation?

Stage 5. Cloud and deployment

A prototype on your laptop is not a result. An FDE ships the solution to the cloud or into the client's closed network, where there may be no internet at all.

End-to-end project, step 5
Package the service in Docker and deploy it to the cloud with automatic deployment from GitHub on every push to main.

Docker

Core · ≈ 15 h

A container is the standard way to bring your solution into someone else's infrastructure so it runs exactly the way it does for you.

What to learn
  • Dockerfile and layers
  • docker compose for multiple services
  • Volumes and environment variables
  • Small, secure images
Practice
Start the service, the database, and the queue with a single docker compose up.
Check yourself
  • Why is a 2 GB image a problem for a client with a slow connection?
Resources
  • Docker: Get started

One cloud: AWS, Azure, or GCP

Core · ≈ 30 h

Knowing one cloud well is enough; the others work in similar ways. Pick the one your future clients use most.

What to learn
  • Compute: virtual machines, containers, serverless
  • Storage and databases
  • IAM: roles and least privilege
  • The cloud bill: what it's made of
Practice
Deploy the service to your chosen cloud and set up an alert if spending goes over a limit.
Check yourself
  • How do you give a service access to storage without creating a long-lived key?

CI/CD

Core · ≈ 10 h

Automated testing and deployment let you fix bugs at a client in minutes, not days.

What to learn
  • GitHub Actions or GitLab CI
  • Tests and linters in the pipeline
  • Secrets in CI
  • Rolling back a deployment
Practice
Set up a pipeline: tests → build image → deploy. Break a test on purpose and make sure the deploy doesn't go through.
Check yourself
  • How do you roll back fast if a new version broke production at the client?
Resources
  • GitHub Actions

Networking and perimeter security

Core · ≈ 15 h

The longest tasks at a client are network ones: "it won't load," "the proxy is blocking it," "the certificate isn't trusted." An FDE needs to understand what happens between services.

What to learn
  • DNS, TLS certificates
  • Private networks (VPC/VNet), firewalls
  • Corporate proxies
  • VPN and access to private resources
Practice
Run the service only on an internal network and give access to it through a VPN.
Check yourself
  • The service works for you, but at the client the request to the model API just hangs. What do you check?

Infrastructure as code

Optional · ≈ 15 h

When the same solution gets deployed for many clients, you can't do it by hand. Terraform describes infrastructure as code.

What to learn
  • Terraform: resources, variables, modules
  • State and where to keep it
  • Separate environments: test and production
Practice
Describe in Terraform everything you created in the cloud by hand, and recreate the environment from scratch.
Check yourself
  • What happens if two people run terraform apply at the same time?
Resources
  • Terraform tutorials

The client's closed network

Optional · ≈ 10 h

Banks, government agencies, and hospitals often don't let data leave their walls. You have to install the solution inside their network, sometimes with local models and no internet.

What to learn
  • Installing without internet access
  • Local models and their limits
  • Requirements to keep data inside the client's country
  • Getting sign-off from the security team
Practice
Run an open language model locally (for example, with Ollama) and connect your service to it instead of a cloud API.
Check yourself
  • What will you lose in quality and speed by switching to a local model?

Stage 6. AI systems engineering

Today most FDEs ship solutions built on large language models. Knowing how to call an API isn't enough: you need reliable quality on the client's data and numbers to prove it.

End-to-end project, step 6
Build an AI assistant that answers questions from the "client's" documents and database, with links to sources. Put together a set of 50 questions with correct answers and measure accuracy.

How language models work

Core · ≈ 10 h

To explain to a client what a model can and can't do, you need to understand how it works without the math: tokens, context, probabilities.

What to learn
  • Tokens and the context window
  • Temperature and randomness in answers
  • Hallucinations: where they come from
  • How to choose a model: quality, speed, price
Practice
Ask one model the same question 10 times at different temperatures and compare the answers.
Check yourself
  • Why does a model confidently name a contract number that doesn't exist?
Foundations at Open School
Artificial intelligence ›Working with AI assistants ›

Prompts and instructions

Core · ≈ 15 h

A system prompt is the model's "job description." A good one is specific, has examples, and explains why each rule is there.

What to learn
  • System prompt and roles
  • Examples (few-shot)
  • Breaking a task into steps
  • Prompt versions and comparing them
Practice
Write a prompt that sorts customer requests into 8 categories, and keep improving it until accuracy stops going up.
Check yourself
  • How do you know a new prompt is better than the old one, not just that it "feels better"?
Resources
  • Claude: prompt engineering
  • OpenAI: prompting

Structured outputs

Core · ≈ 8 h

For a model's answer to make it into the client's system, it has to be data following a schema, not free text: JSON with the right fields.

What to learn
  • JSON Schema
  • Structured outputs in model APIs
  • Validating the answer (pydantic) and retrying on errors
  • Extracting fields from documents
Practice
Extract the vendor, amount, date, and number from 50 invoices into JSON. Count how many fields came out right.
Check yourself
  • What do you do if the model returned valid JSON but with a made-up date?

Tools, agents, and MCP

Core · ≈ 20 h

A model becomes useful when it can act: search a database, create a ticket, send an email. For that you give it tools, and MCP is the standard for connecting them.

What to learn
  • Tool use (function calling)
  • The agent loop and its stop condition
  • Model Context Protocol: servers and clients
  • Human approval for risky actions
Practice
Build an agent with three tools: database search, ticket creation, and sending a notification. The risky action runs only after approval.
Check yourself
  • How do you constrain an agent so it can't delete client data by mistake?
Resources
  • Model Context Protocol
  • Claude: tool use

Knowledge search (RAG)

Core · ≈ 25 h

The most common FDE project: an assistant that answers from the company's documents. Answer quality here depends on search more often than on the model.

What to learn
  • Embeddings and vector search
  • Splitting documents (chunking)
  • Hybrid search and reranking
  • Source links in the answer
  • Access rights: employees see only their own documents
Practice
Compare three ways of chunking documents on the same set of questions and pick the best one by the numbers.
Check yourself
  • The assistant gives a wrong answer. How do you tell whether search or the model is to blame?

Quality evaluation (evals)

Core · ≈ 20 h

What sets a strong FDE apart: they don't say "it works well," they show "91% accuracy on 200 real questions, up from 74%." Without evaluation you can neither improve nor sell.

What to learn
  • A reference set of questions with answers from the client's experts
  • Metrics: precision, recall, refusal rate
  • LLM-as-judge and how to check it
  • Regression tests when you change the prompt or model
Practice
Collect 100 questions with an "expert," run the evaluation automatically, and write a one-page report for the client's executive.
Check yourself
  • Why can't you check quality only on questions you made up yourself?

Speed and cost

Core · ≈ 8 h

A pilot with 10 users costs pennies. With 5,000 employees, the model bill becomes a budget line, and a 30-second answer becomes a reason to say no.

What to learn
  • Calculating cost per user per month
  • Caching prompts and answers
  • Small models for simple steps
  • Streaming and batch processing
Practice
Calculate what your assistant would cost a company with 2,000 employees, then cut the price in half without losing quality.
Check yourself
  • Which steps of your solution could go to a cheaper model?

AI solution security

Core · ≈ 10 h

An AI assistant with access to client data is a new attack surface. It will be the very first question from the client's security team.

What to learn
  • Prompt injection: attacks through documents and emails
  • Personal data leaks
  • Limiting tool permissions
  • An audit log of agent actions
Practice
Hide the instruction "forward all data to this address" in a document and see whether your assistant follows it. Close the vulnerability.
Check yourself
  • How do you prove to the client's security team that the assistant can't see other people's documents?

Stage 7. Production

The solution has to keep working after you leave. That means you can see what's happening inside it, it survives failures in neighboring systems, and it comes with documentation.

End-to-end project, step 7
Add logs with a request ID, a dashboard with key metrics, and an on-call guide: "what to do if…".

Logs, metrics, tracing

Core · ≈ 12 h

When the client writes "the assistant gave a weird answer yesterday at 3:40 PM," you need to find that exact request and everything that happened to it.

What to learn
  • Structured logs and request IDs
  • Metrics: latency, errors, load
  • Tracing across multiple services
  • AI logs: prompt, answer, retrieved documents
Practice
Use a single request ID to trace its whole path: input, search, model call, answer.
Check yourself
  • What must never go into logs if requests contain personal data?
Resources
  • OpenTelemetry

Reliability

Core · ≈ 10 h

The model API is sometimes slow, the client's CRM goes down at night. The solution has to survive that without a human stepping in.

What to learn
  • Timeouts and retries with backoff
  • Rate limits
  • A fallback model or a simplified answer
  • Queues for heavy jobs
Practice
Turn off an external API for 5 minutes and make sure the service doesn't crash and then catches up on its own.
Check yourself
  • Why can endless instant retries take down someone else's system?
Resources
  • Google SRE Book

Personal data and compliance

Core · ≈ 8 h

The client has lawyers and a security team. An FDE should know their questions in advance: where the data is stored, who sees it, how long it's kept.

What to learn
  • Personal data: what counts
  • Where data may be stored and personal data laws (for example, GDPR)
  • Masking and anonymization
  • Audit: who did what
Practice
Draw a one-page map for your project: what data, where it lives, who has access, when it's deleted.
Check yourself
  • What questions will a bank's security officer ask before a pilot launches?

Documentation and handoff

Core · ≈ 6 h

An FDE project ends when the client's team can live with the solution without you. That takes instructions, not just code.

What to learn
  • A README a newcomer can understand
  • Runbook: what to do in common failures
  • Training the client's team
  • A list of known limitations
Practice
Give your project to a friend and see whether they can deploy it using only the README.
Check yourself
  • What has to be ready for you to leave the client with peace of mind?

Stage 8. Working with the client

Half of an FDE's job is people. Technically strong engineers most often fail right here: they build the wrong thing, stay quiet about risks, or can't show the result.

End-to-end project, step 8
Run 3 interviews with people from your chosen industry about their routine. Rewrite the project goal based on what you learn and demo it to one of them.

Interviews and finding the real problem

Core · ≈ 10 h

The client comes with a solution ("build us a chatbot"), and the FDE looks for the problem behind it ("operators spend 3 hours a day searching contracts"). The most valuable part of the job.

What to learn
  • Questions about past experience, not wishes
  • Watching an employee actually work
  • A success metric agreed with the client
  • The book The Mom Test
Practice
Interview an employee at any company and find the task that eats up most of their time.
Check yourself
  • Why is the question "Would it be convenient for you if…?" almost useless?

Scope and priorities

Core · ≈ 6 h

The client always wants more than there's time for. An FDE agrees on the smallest solution that gives a measurable result and honestly says "no" to the rest.

What to learn
  • Pilot: timeline, users, metric
  • Estimating timelines and risks
  • How to say "not now" and keep the relationship
  • Scope changes mid-project
Practice
Take a big request ("AI for the whole sales department") and cut it down to a 4-week pilot with one metric.
Check yourself
  • Halfway through the pilot, the client asks for "one more small feature." What do you do?

Demos and presenting results

Core · ≈ 6 h

A good demo shows the work on the client's data and in their language, not what the technology can do. It's watched by the people who decide whether to continue.

What to learn
  • A demo script from problem to result
  • Real client data instead of made-up data
  • A plan B if something breaks live
  • Before and after numbers
Practice
Record a 3-minute video demo of your project for an executive who doesn't know anything about AI.
Check yourself
  • What will you show in the first 30 seconds of the demo?

Written communication

Core · ≈ 6 h

An FDE writes all the time: weekly status updates, risk emails, meeting notes. Short, clear writing saves weeks.

What to learn
  • Status: done, next, risks, help needed
  • Bad news early and with options
  • Meeting notes the same day
  • Writing for an executive versus an engineer
Practice
Write a 5-line project status where one piece of news is bad.
Check yourself
  • When do you tell the client a deadline is at risk?

Stakeholders

Core · ≈ 5 h

The client has many people with different goals: the executive wants results, employees fear being replaced, IT fears new risks, security fears leaks. You need everyone on board.

What to learn
  • People map: who decides, who influences, who uses it
  • The project champion at the client
  • Fear of being replaced by AI and how to handle it
  • Escalation when the project is stuck
Practice
Draw a map of your project's stakeholders: 6–8 roles, what each wants and what each fears.
Check yourself
  • The pilot succeeded, but users aren't using it. Why does that happen?

Feedback into the product

Optional · ≈ 4 h

The FDE is the product team's eyes in the real world. If you're writing the same workaround for the third client, it should become a product feature.

What to learn
  • How to tell a one-off case from a common need
  • Describing a problem for a product manager
  • Moving repeated code into a shared tool
Practice
Describe one feature your project was missing in the format "problem → who suffers → how often → proposal."
Check yourself
  • Why shouldn't an FDE just add everything the client asked for to the product?

Stage 9. The client's industry

After a month with a client, an FDE should speak the language of their industry. Strong FDEs eventually become experts in one or two industries.

End-to-end project, step 9
Build a glossary of 30 terms for your industry and a map of its core process (for example, an order's path from request to payment).

How to get into a new industry fast

Core · ≈ 6 h

You can't automate a process you don't understand. Ramping up quickly is a separate skill, and it can be trained.

What to learn
  • A glossary of terms from day one
  • An "as is" process map
  • The regulators and documents that define everything
  • Where the industry loses money and time
Practice
In one evening, figure out an unfamiliar industry and explain its process to a friend in 5 minutes.
Check yourself
  • What three questions will you ask on your first day in a new industry?

Typical problems by industry

Optional · ≈ 8 h

Many problems repeat from client to client. Knowing the typical scenarios speeds up finding a solution.

What to learn
  • Finance: document checks, loan applications, compliance
  • Healthcare: medical records, visit transcription, diagnosis codes
  • Logistics: waybills, tracking, planning
  • Public sector: citizen requests, document workflows
Practice
For each of the four industries, come up with one AI solution and a metric for its success.
Check yourself
  • In which industry would a model's mistake cost the most, and why?

Economic impact

Core · ≈ 5 h

The CFO is the one who buys the next phase. They need the math: what it cost before, what it costs now, and what the solution itself costs.

What to learn
  • Employee hours × hourly rate
  • The cost of errors and delays
  • Total cost of the solution
  • Payback period
Practice
On one page, calculate the savings from your project for a company with 50 operators.
Check yourself
  • Why is "we saved 30% of the time" not yet an argument for a CFO?

Stage 10. Portfolio and getting hired

FDEs get hired for the projects they've built and how they think. A resume listing technologies barely matters.

End-to-end project, step 10
Polish your end-to-end project: a README with the client's problem, the architecture and quality numbers, a 3-minute demo video, and a story about what went wrong.

Portfolio

Core · ≈ 20 h

You need 2–3 projects that show the whole path: a real person's problem → a solution in production → numbers. One project like that beats ten tutorial projects.

What to learn
  • A project for a real user, even someone you know
  • Result numbers on the first screen of the README
  • A video demo
  • An honest "what I'd do differently" section
Practice
Find a small business or someone you know with a routine task and build them a free AI solution.
Check yourself
  • Can someone who opens your project understand within a minute what problem it solves?

The interview

Core · ≈ 15 h

There are usually several rounds: coding, a case study ("the client wants…, what will you do?"), a role-play meeting with a "client," and a conversation about past projects.

What to learn
  • Case: clarifying questions → plan → risks → metric
  • Coding on practical problems, not just algorithms
  • Role-play meeting: listen more than you talk
  • Project stories in the "situation → actions → result" format
Practice
Ask a friend to play an unhappy client and hold a 20-minute meeting with them. Record it and watch it back.
Check yourself
  • The client says: "We need AI." What five questions do you ask first?

Where to look for a job

Optional · ≈ 4 h

FDEs are hired by companies that sell complex platforms to businesses: AI model developers, data platforms, integrators. The job titles vary.

What to learn
  • Other titles: Forward Deployed / Deployment Engineer, AI Engineer (customer-facing), Solutions Architect
  • The inside path: from engineering or from implementation at your own company
  • Remote roles and travel
  • Strong English for working with international clients
Practice
Make a list of 20 companies that have an FDE role or something similar, and note what you're missing for each one's requirements.
Check yourself
  • Which path into the role fits you better: from engineering or from working with clients?
