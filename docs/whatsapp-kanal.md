# Второй канал: переписка в WhatsApp

Тот же ассистент, что отвечает по телефону, отвечает и в переписке. Анкета
одна: правите услуги или цены — меняется и голос, и текст.

Схема: **WhatsApp → шлюз OpenWA на Render → вебхук на наш сервер → ответ →
обратно через шлюз.** Ничего не крутится на вашем компьютере.

## Что где живёт

| Часть | Где | Зачем |
|---|---|---|
| Шлюз OpenWA | отдельный сервис на Render | держит сессию WhatsApp, принимает и отправляет сообщения |
| Приём и ответ | `/api/whatsapp/inbound` на нашем сервере | узнаёт арендатора, строит ответ по анкете, зовёт шлюз |
| Отправка | `WA_API_URL` / `WA_API_KEY` / `WA_SESSION` в настройках Azure | адрес и ключ шлюза |

Шлюз вынесен отдельным сервисом нарочно: он держит живую сессию и Chromium,
и его перезапуск не должен ронять сайт, а деплой сайта — сессию, после
которой придётся заново сканировать QR.

## Развернуть шлюз

1. render.com → **New → Web Service → Existing image**, образ
   `ghcr.io/rmyndharis/openwa:latest`. Либо Blueprint из
   [deploy/openwa/render.yaml](../deploy/openwa/render.yaml).
2. План — **Standard (2 ГБ)**. На Starter с 512 МБ движок whatsapp-web.js не
   поместится: это настоящий Chromium.
3. Диск: **1 ГБ, точка монтирования `/app/data`**. Без него сессия не переживёт
   перезапуск.
4. Переменные: `PORT=2785`, `DATABASE_URL=file:/app/data/openwa.db`,
   `ADMIN_API_KEY` — придумать и сохранить, это первый ключ панели.
5. Открыть панель по адресу сервиса, создать сессию, **выбрать движок
   whatsapp-web.js** (не baileys: авторы пишут, что его WhatsApp вычисляет
   легче и банит чаще), отсканировать QR.
6. Выпустить рабочий API-ключ (роль operator, привязать к этой сессии).

## Связать со своим сервером

В настройках Azure (App Service → Configuration) добавить три значения:

```
WA_API_URL   = https://<имя сервиса>.onrender.com
WA_API_KEY   = ключ operator из панели OpenWA
WA_SESSION   = идентификатор сессии
```

И сказать шлюзу, куда слать входящие. Ключ в адресе — это `tool_key`
арендатора: по нему сервер понимает, чья это переписка, и он же служит
пропуском.

```bash
curl -X POST https://<сервис>.onrender.com/api/sessions/<сессия>/webhooks \
  -H 'Content-Type: application/json' -H 'X-API-Key: <ключ>' \
  -d '{"url":"https://reception365.online/api/whatsapp/inbound?k=<tool_key>",
       "events":["message.received"]}'
```

## Проверка

Написать на подключённый номер с другого телефона: «есть что-то на 12–14
сентября на двоих?». Ответ должен прийти со свободными вариантами и суммой за
срок. В логах Azure — строка `[whatsapp] <арендатор> ...` с вопросом и ответом.

Если тихо: смотрите логи сервиса на Render (дошёл ли вебхук) и логи Azure
(ответили ли мы). Пустой ответ с нашей стороны почти всегда значит, что не
заданы `WA_*` — тогда ответ построен, но отправлять его некуда.

## Про баны

Шлюз неофициальный: он логинится как веб-клиент. WhatsApp за автоматизацию
номера блокирует, и вернуть номер нельзя — только апелляция в Meta.

- Дата-центровые адреса Render флагуются агрессивнее домашних. Следующий шаг —
  пустить трафик через residential-прокси, OpenWA поддерживает прокси на
  сессию.
- Отвечать тем, кто написал сам, — самый безопасный режим. Первым писать
  незнакомым номерам нельзя: по словам авторов, это надёжнейший способ
  получить блокировку.
- Ограничитель в конфиге стоит на две отправки в минуту.
- Для клиник этот путь не годится: авторы OpenWA прямо относят здравоохранение
  к областям, где их шлюз применять не следует. Там официальный WhatsApp Cloud
  API. Наш сервер к смене шлюза готов: он знает только «пришло сообщение — дай
  ответ».

## Запасной путь: шлюз на своей машине

Если шлюз окажется удобнее держать локально, есть
[wa-connector.js](../scripts/wa-connector.js): он принимает вебхук на
localhost, спрашивает ответ у `/api/whatsapp/reply` и отправляет обратно. Тогда
наружу ходит только он, и открывать домашний роутер не нужно.
